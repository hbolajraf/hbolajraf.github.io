.NET | Reconcile Two Lists with LINQ FullJoin

Posted Nov 22, 2026
By Hassan BOLAJRAF 2 min read

Imagine comparing a product catalog with a warehouse count. Some products appear in both lists; others exist in only one. An inner join hides those missing records, which are often the very records you need to investigate.

.NET 11 adds LINQ FullJoin. It keeps matched records and the unmatched records from both sequences. Let’s use it to find the differences between an expected inventory and an actual count.

What does a full join return?

Key Expected list Actual list Result
A100 10 8 Both records
B200 5 Missing Expected record and a missing actual record
C300 Missing 3 Missing expected record and actual record

The missing side is default: for reference types such as the records below, that means null.

Try it with .NET 11

1

dotnet new console -n InventoryCompare -f net11.0

using System;
using System.Linq;

Inventory[] expected =
[
    new("A100", 10),
    new("B200", 5)
];

Inventory[] actual =
[
    new("A100", 8),
    new("C300", 3)
];

var comparison = expected
    .FullJoin(actual, item => item.Sku, item => item.Sku)
    .OrderBy(pair => pair.Outer?.Sku ?? pair.Inner?.Sku,
             StringComparer.Ordinal);

foreach (var (planned, counted) in comparison)
{
    var sku = planned?.Sku ?? counted?.Sku ?? "unknown";
    var plannedText = planned is null ? "missing" : planned.Quantity.ToString();
    var countedText = counted is null ? "missing" : counted.Quantity.ToString();

    Console.WriteLine($"{sku}: expected={plannedText}, actual={countedText}");
}

record Inventory(string Sku, int Quantity);

Run it:

1

dotnet run --project InventoryCompare

Expected output:

1
2
3

A100: expected=10, actual=8
B200: expected=5, actual=missing
C300: expected=missing, actual=3

The OrderBy makes this example’s output easier to read. The join itself returns tuples named Outer and Inner; here those represent the expected and actual records.

Things to check in a real application

  • Duplicate keys: if a key appears multiple times on both sides, a join can return multiple combinations. Decide whether to aggregate or reject duplicates first.
  • Key comparison: normalize identifiers or supply an appropriate comparer when case matters. A100 and a100 may be different keys under the default string comparison.
  • Missing versus zero: a missing record is not necessarily a quantity of zero. Decide how your domain should treat each case before calculating differences.
  • Database queries: this example uses in-memory Enumerable.FullJoin. Provider translation and database support can differ; inspect generated SQL and test your actual Entity Framework provider before relying on server-side translation.
