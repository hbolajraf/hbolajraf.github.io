.NET | Exploring .NET 11 and Runtime Async

Posted Nov 22, 2026
By Hassan BOLAJRAF 2 min read

.NET 11 is here, with updates to the runtime, SDK, libraries, ASP.NET Core, and C#. This article looks at a few changes that matter to application teams and shows how to evaluate the new Runtime Async compilation model.

Microsoft released .NET 11 on November 10, 2026. It is a standard-term support (STS) release; .NET 10 remains a long-term support (LTS) option. Both are supported until November 2028 according to Microsoft’s support information. Choose based on your application’s requirements and keep the selected runtime patched.

What changed?

Faster developer workflows

The .NET 11 SDK uses a Native AOT CLI host by default for certain commands, and its MSBuild server stays warm between CLI invocations. These improvements target everyday command overhead; the actual benefit depends on the project and environment.

Runtime and library improvements

The runtime includes JIT optimizations and other performance improvements. The libraries add built-in Zstandard compression and new APIs for working with processes and in-memory data. LINQ also adds FullJoin, which can help compare two collections while retaining unmatched items from either side.

Performance changes are workload-dependent. Benchmark your own application rather than assuming every endpoint will improve by the same amount.

ASP.NET Core and C#

The release includes asynchronous validation and OpenAPI 3.2 support in ASP.NET Core, alongside new C# 15 language capabilities. Check framework and package compatibility before changing a production target.

Runtime Async: a feature to evaluate

Runtime Async moves asynchronous suspension and resumption into the runtime instead of relying on the usual compiler-generated state-machine approach. One potential benefit is clearer live call stacks when debugging or profiling async code. It also changes the performance characteristics of async operations, so measure it with representative workloads.

Runtime Async remains a preview feature in .NET 11. The runtime libraries use it, but that does not automatically opt your own application code in. For an experiment targeting net11.0, add this to the project file:

1
2
3
4

<PropertyGroup>
  <TargetFramework>net11.0</TargetFramework>
  <Features>runtime-async=on</Features>
</PropertyGroup>

You do not need EnablePreviewFeatures for this particular setting. Try it on a branch first, verify your dependencies and diagnostics, and compare results with the setting disabled. Microsoft’s release announcement links to the detailed Runtime Async guidance.

Try a clean .NET 11 project

Install the .NET 11 SDK, then run:

1
2
3

dotnet --list-sdks
dotnet new console -n HelloDotnet11 -f net11.0
dotnet run --project HelloDotnet11

For an existing service, installing the SDK alone does not change the application’s target framework. Update the target and compatible packages deliberately, review breaking changes and minimum CPU requirements, and test the actual deployment image and native dependencies.

Upgrade checklist

  1. Check global.json, developer machines, build agents, and container images for SDK and runtime versions.
  2. Review package and workload compatibility, then update the target framework.
  3. Run unit, integration, and deployment tests; compare startup time, memory, and throughput with a baseline.
  4. Test your publishing mode: framework-dependent and self-contained deployments receive runtime updates differently.
  5. Treat preview features as experiments until their status and your risk tolerance permit wider adoption.
