DevOps | Protecting GitHub Actions Workflow Execution

Posted Nov 22, 2026
By Hassan BOLAJRAF 2 min read

Your CI pipeline can build code, access credentials, and publish artifacts. That makes control over who can run a workflow and which events can start it an important part of your security design. In September 2026, GitHub announced that workflow execution protections were generally available.

What are execution protections?

These protections let administrators define allowlists for workflow execution. Actor rules describe who may trigger a run, while event rules describe which events may start it. Rules can target specific workflow files, so a team can apply stricter controls to deployment workflows while keeping ordinary CI available to contributors.

For example, a team might allow pull requests to run tests, but restrict a production deployment workflow to a designated group and approved events. Design the rules around the actual contributors and deployment process, then use the available insights to review their effects. Check your GitHub plan, permissions, and current documentation before configuring organization or enterprise policies.

Start with a small .NET CI workflow

The following example restores, builds, and tests a .NET solution. Put it in .github/workflows/dotnet-ci.yml in a repository containing a solution file at its root. Replace the SDK version if your project targets a different supported release.

name: .NET CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '10.0.x'
      - name: Restore
        run: dotnet restore
      - name: Build
        run: dotnet build --configuration Release --no-restore
      - name: Test
        run: dotnet test --configuration Release --no-build

This example only needs read access to repository contents and does not deploy anything. For a production workflow, review third-party actions and consider pinning them to verified full commit SHAs; version tags can move. Keep those pins updated through a reviewed dependency update process.

Keep trust boundaries clear

Be especially careful with pull_request_target: it runs in the context of the base repository and can have access to privileges and secrets. Checking out and executing untrusted pull request code in that context can expose the pipeline. Prefer a regular pull_request workflow for building untrusted contributions, and separate privileged publishing into a carefully controlled workflow.

Execution protections add a layer of control; they do not replace least-privilege token permissions, protected environments, secret scoping, action review, or safe handling of untrusted input.

A practical rollout

  1. Inventory workflows, their triggers, token permissions, secrets, and deployment targets.
  2. Identify privileged workflows and the people or automation that legitimately run them.
  3. Configure appropriately scoped actor and event rules, starting with a nonproduction repository or a limited target.
  4. Test normal and denied scenarios, including contributor pull requests and emergency releases.
  5. Monitor protection insights and adjust rules without weakening required controls.
