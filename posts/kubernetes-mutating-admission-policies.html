Kubernetes | Default Pod Labels with Mutating Admission Policies

Posted Nov 22, 2026
By Hassan BOLAJRAF 2 min read

A platform team might want new Pods in a test namespace to carry an owner label. Asking every developer to remember the label works until someone forgets. A mutating admission policy can add a default during the API request, before Kubernetes stores the Pod.

MutatingAdmissionPolicy became stable in Kubernetes 1.36. It uses CEL expressions in the API server and can replace some webhook use cases. A policy describes the mutation; a separate binding activates it and can narrow its scope.

Policy versus binding

Object Job in this example
MutatingAdmissionPolicy Add an owner label to matching new Pods when it is absent.
MutatingAdmissionPolicyBinding Apply that policy only to the admission-lab namespace.

This example is for a disposable test cluster running Kubernetes 1.36 or later. You need permission to create cluster-scoped admission policies and bindings. Admission policies can affect API requests; review the scope carefully before using them in a shared cluster.

1. Create a test namespace

1

kubectl create namespace admission-lab

Use a fresh name if that namespace already exists. If you change the name, update the binding and later commands too.

2. Define the policy and binding

Save the following as owner-policy.yaml:

apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicy
metadata:
  name: default-pod-owner.example.com
spec:
  reinvocationPolicy: IfNeeded
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: ["v1"]
        operations: ["CREATE"]
        resources: ["pods"]
  matchConditions:
    - name: owner-label-is-missing
      expression: "!has(object.metadata.labels) || !('example.com/owner' in object.metadata.labels)"
  mutations:
    - patchType: ApplyConfiguration
      applyConfiguration:
        expression: >
          Object{metadata: Object.metadata{labels: {'example.com/owner': 'platform-team'}}}
---
apiVersion: admissionregistration.k8s.io/v1
kind: MutatingAdmissionPolicyBinding
metadata:
  name: default-pod-owner.example.com
spec:
  policyName: default-pod-owner.example.com
  matchResources:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: admission-lab

Apply it:

1

kubectl apply -f owner-policy.yaml

The policy watches Pod CREATE requests; the binding narrows it to the test namespace. If a Pod already has example.com/owner, the match condition leaves that value alone. Existing Pods are not retroactively changed. The namespace name label is managed by Kubernetes, which makes it useful for selecting this specific namespace.

3. Test with a server-side dry run

Create demo-pod.yaml:

1

apiVersion: v1
kind: Pod
metadata:
  name: admission-demo
spec:
  containers:
    - name: demo
      image: busybox:1.36
      command: ["sh", "-c", "sleep 300"]

Ask the API server to process the request without persisting the Pod:

1

kubectl create -n admission-lab --dry-run=server -f demo-pod.yaml -o yaml

Look for example.com/owner: platform-team under metadata.labels. Then add a different owner label to the manifest and repeat: the provided value should remain. If the label is absent, check the policy and binding names, namespace selector, API version, and kubectl describe mutatingadmissionpolicy default-pod-owner.example.com for reported status.

4. Clean up the test

Only remove the resources you created for this exercise:

1
2
3

kubectl delete mutatingadmissionpolicybinding default-pod-owner.example.com
kubectl delete mutatingadmissionpolicy default-pod-owner.example.com
kubectl delete namespace admission-lab

A default is not an enforcement rule: someone allowed to set or change a label can choose another value. Use an appropriate validating policy if you need to require an allowed value, and review authorization and failure behavior separately.
